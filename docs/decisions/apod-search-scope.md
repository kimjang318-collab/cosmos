# APOD 검색 범위

## Decisions

- 키워드 검색은 전체 NASA APOD 기록(1995-06-16~오늘)을 대상으로 한다.
- 전체 기록은 Vercel Blob에 JSON 인덱스(날짜·제목·설명)로 저장해두고, 검색은 이 인덱스를 읽어서 걸러낸다. NASA API를 검색 시점마다 직접 호출하지 않는다.
- 인덱스는 한 번 전체를 채우는 백필 스크립트(로컬에서 1회 실행)로 초기화하고, 이후에는 하루 1회 Vercel Cron Job이 빠진 날짜만 채워 넣는다.

## Boundaries

- 이 결정은 키워드 검색 기능에만 적용된다. 날짜를 직접 선택해 과거 사진을 보는 기능([docs/specs/apod-date-picker/spec.md](../specs/apod-date-picker/spec.md))은 이 인덱스와 무관하게 NASA API를 그때그때 호출한다.
- Cron Job의 실제 스케줄 실행과 배포 환경에서의 동작은 로컬에서 완전히 검증할 수 없다 — 로컬에서는 그 라우트를 직접 호출해 로직만 확인한다.

## Why

처음에는 저장소 없이 "검색 시점마다 최근 기간만 즉시 조회"하는 가벼운 방식(최근 1년)을 시도했다. 그런데 실제로 확인해보니 NASA APOD의 `start_date`/`end_date` 조회 자체가 매우 느렸다 — 30일에도 약 5초, 90일에 약 15초가 걸렸고, 애초에 목표했던 365일 조회는 NASA 서버가 30초 뒤 500 에러로 응답해 아예 실패했다(curl로 직접 확인). 즉 저장소 없이는 "최근 1년 검색"이라는 원래 목표 자체가 성립하지 않았다.

반면 Vercel Blob에 전체 기록을 미리 저장해두면, 검색 시점의 응답은 저장된 JSON을 읽어 메모리에서 걸러내는 정도라 빠르다. Vercel Hobby(무료) 플랜에서도 Cron Job은 하루 1회까지 무료로 지원되고, 서버리스 함수 실행 시간 제한(기본 300초)도 충분히 넉넉해 이 방식이 실제로 가능하다는 것을 확인했다.

## Reconsider when

- NASA APOD API가 더 빠른 range 조회나 자체 검색 기능을 지원하게 될 때.
- Vercel Blob 사용량(용량·요청 수)이 무료 한도를 넘어서기 시작할 때.

## Still-rejected alternatives

- 검색 시점마다 최근 N일을 NASA에 직접 조회 — 실제로 30일 이상 구간에서 5초 이상 걸리고, 목표했던 1년 구간은 NASA 서버가 500 에러로 실패하는 것을 확인해 폐기했다. 저장소 없이 가려던 원래 의도(설정 부담 최소화)와 달리, 저장소를 두는 쪽이 오히려 더 빠르고 안정적이었다.
